# Onboarding — tsforecastbench

Welcome. This is a one-sitting path from a fresh clone to your first contribution.
It sequences the existing docs rather than repeating them; follow it top to bottom.

- **What this project is:** a forecasting benchmark for water & environment — naive
  baselines → classical → windowed-ML → foundation models, across 11 open cases.
  Start with the [`README.md`](README.md) intro and the case/method tables.
- **Why it exists & where it's going:** [`research_plan.md`](research_plan.md) (RK2026 / KER5).

## 1. Get it running (~10 min)

```bash
git clone <repo> && cd timeseries-forecasting-benchmark
uv sync                                  # core deps; processed data (~16 MB) is committed
uv run pytest -q                         # runs on synthetic + committed data — no network/GPU
uv run python scripts/run_pilot.py --fast   # smoke the full pipeline (single hold-out)
```

A fresh clone runs immediately — no downloads. If you're on **WSL with a GPU** and want the
neuralforecast zoo / CUDA torch, use the one-shot setup instead: `bash scripts/bootstrap_wsl.sh --gpu`.

## 2. Explore the data and results interactively (~20 min)

Two [marimo](https://marimo.io) notebooks — reactive, browser-based:

```bash
uv sync --extra notebooks
uv run marimo run notebooks/eda.py        # per-case EDA: map, splits, ACF, exogenous CCF + MI
uv run marimo run notebooks/results.py    # scoreboard, skill ranking, example & hardest-window forecasts
```

Use the **case dropdown** at the top to switch cases. `results.py` runs rolling-origin
scoring on first view of a case (8 origins by default) and caches to `notebooks/.cache/`,
so the first load is slow and the rest instant.

> Gotcha: if you open a notebook with `marimo edit` and it writes a `# /// script` block at
> the top, delete it — it makes `uv run` build an isolated env without the project deps.

## 3. Understand the science (~15 min)

- [`docs/RESULTS.md`](docs/RESULTS.md) — the cross-case findings in one place.
- [`docs/reports/`](docs/reports/) — a one-page report per case (scores, example forecast,
  error-vs-lead-time), regenerated by `scripts/case_report.py`. Read these for the shape of a
  case, not for its numbers: each one comes from its own `case_report.py` run rather than from
  the published matrix, and none has been regenerated since. Their MASE in particular predates
  the pinned dominant period (research log entry 103), so it does not match the app.

The headline results to internalise:

- **Covariates help where physics says they should** (8/11 cases): stream-temp skill-vs-persistence
  +0.35→+0.84, storm surge +0.00→+0.52, snowmelt −0.08→+0.47. The clean null is **groundwater**
  (it integrates recharge, so day-ahead covariates add little).
- **Chronos-Bolt zero-shot** wins the flashy river (+0.80) and is strong on regular signals
  (demand, WWTP flow) — a strong but **regime-dependent** free prior.
- **Honest failure modes:** covariates can *hurt* (bellinge 15-min rain +0.31→−0.45); univariate
  LightGBM is brittle on flashy daily flow; MLP is the least robust; SeasonalNaive is a trap on
  trending hydrology.

## 4. Map of the repo

Two namespaces, intended to be separable (and eventually two repos):

- **`tsforecastbench.data`** — case building: `schema.py` (the `Case` model), `registry.py`
  (auto-discovers `cases/*/case.toml`), `cases/` (one folder per case: `case.toml`, `synth.py`,
  `download.py`), and the shared `_usgs`/`_ndbc`/`_era5` fetchers.
- **`tsforecastbench.bench`** — model comparison: `methods/` (every forecaster), `eval/`
  (rolling-origin loop, metrics, the `DEFAULT_ORIGINS` knob), `viz/`. `bench` touches `data`
  **only** through the public `Case` interface.

Entry points in `scripts/`:

| script | what it does |
|---|---|
| `run_pilot.py` | the cases × methods matrix (`--with-fm/-dl/-nf`, `--fast`, `--origins`) |
| `run_leadtime.py` | error-vs-lead-time curves for one case |
| `case_report.py` | the per-case Markdown reports under `docs/reports/` |
| `case_eda.py` | quick text EDA for a case |
| `review_case.py` | quality-gate a case (also the `/review-case` skill) |
| `print_results.py` | plain-text dump of the latest run |
| `precheck.py` | **run before pushing** — ruff + pytest + shows uncommitted files |

## 5. How we work

- **PR-only.** Direct push to `main` is blocked. Branch → `gh pr create` → wait for CI
  (`gh pr checks`) → `gh pr merge --merge`. Run `uv run python scripts/precheck.py` first so a
  red CI isn't a surprise.
- **Adding a case or method** is a local change against a common interface — see
  [`CONTRIBUTING.md`](CONTRIBUTING.md). Always run `/review-case <id>` on a new case before
  committing.

## 6. Environment notes

- **Python 3.12.** 3.13 has no `ray` wheels, which the neuralforecast zoo needs.
- **Extras:** `fm` (Chronos-Bolt), `dl` (torch N-HiTS/PatchTST, portable), `nf` (TFT/iTransformer/
  TimesNet — Linux/WSL only), `data` (download deps), `dev` (ruff+pytest), `notebooks` (marimo+plotly).
- **GPU** (if present): tune for your card; the dev laptop's RTX 500 Ada is only 4 GB, so keep
  model/batch sizes modest. `nf_models.py` caps neural training at the last 30 000 points.

## 7. Your first tasks

Good beginner-friendly entry points (see `gh issue list`):

- **#19 — commit distilled scores to `docs/`** so newcomers see results without running the
  pipeline. Self-contained; teaches you the eval output shape.
- **#20 — track train + inference time per method.** Touches the eval loop lightly; useful and bounded.
- **Learning exercise:** add a trivial method (e.g. a drift baseline) by subclassing
  `bench.methods.base.Forecaster`, and run `/review-case` on a case to see the quality gate.

Ask early, push small PRs, and lean on the notebooks to build intuition before changing the eval.
